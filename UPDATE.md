# Обновление документации Core

Процесс запускается по запросу владельца. Скрипты сравнивают источники и строят справочники; агент разбирает смысл изменений и редактирует связанные главы. Расписания, обращения к модели и принятия версии внутри скриптов нет.

## 1. Подготовить пакет

```sh
npm run check:upstream
npm run docs:diff -- --to latest
# Или явно выбрать релиз:
npm run docs:diff -- --to v190
```

`check:upstream`: 0 — изменений нет, 2 — обнаружены изменения, 1 — ошибка. `docs:diff`: 0 — пакет подготовлен, 1 — ошибка. `latest` при подготовке один раз разрешается в максимальную опубликованную версию каталога; затем сравниваются фиксированные version URL. Сам канал latest проверяется отдельно, он может отличаться от максимальной версии.

Старая версия проверяется по сохранённым SHA-256. Недоступность источника или несовпадение хеша останавливает подготовку. Core загружается в память, копии файлов в Git не создаются. Пакет сохраняется в игнорируемом `work/core-update/vBASE-vTARGET-FINGERPRINT/`:

- `report.md` — краткая сводка, связанные главы, примеры и указания по продолжению.
- `api.json` — добавленные и удалённые классы и имена переменных.
- `report.json` — изменения правил/значений с исходным контекстом и порядком, текстовые изменения JS/HTML, непокрытые изменения, хеши входов.
- `candidate-manifest.json` — предложение новой базы; принятую базу команда не меняет.

Если все файлы прежние, разбор модели не требуется. Новый номер при одинаковых файлах требует только проверки метаданных и сборки.

## 2. Разобрать затронутое

Начните с `report.md` и `api.json`. Не загружайте весь `report.json`, собранный HTML или минифицированные файлы в контекст модели. Выберите нужный файл или правило, например:

```sh
jq '.files[] | select(.file == "theme-ss.css") | .changes' work/core-update/<пакет>/report.json
jq '.unmapped' work/core-update/<пакет>/report.json
```

Сопоставление использует упоминания классов/переменных в главах и примерах, ссылки JS-модулей и небольшой `tools/update-dependencies.json`. Это подсказка для отбора, а не доказательство полноты. Root-переменные, регистрации свойств и изменение порядка правил расширяют проверку. `unmapped` требует явного решения: обновить главу/пример, добавить описание или записать, почему пользовательский контракт не изменился. Не игнорируйте изменения ради экономии контекста.

CSS сравнивается по структуре, включая вложенные условия, важность, дубли и порядок деклараций/правил. Для изменённых, добавленных и удалённых блоков `position` сохраняет индекс в обходе исходного дерева и ключи соседей; это позволяет отличить вставку до конкурирующего правила от вставки после него. Совпадение набора классов не означает совпадение поведения. Перенос селектора показывается как удаление/добавление, не как доказанное переименование. Текстовый отчёт JS содержит изменённый диапазон с окружением; при необходимости дочитайте функцию и её зависимости по версионному URL. Неизменившийся JS повторно читать не нужно, но новый CSS может влиять на его компоненты.

Минифицированные варианты хешируются отдельно. Их эквивалентность исходникам не предполагается; изменение только min-файла отмечается для отдельного разбора. Отличия адресов канала в readme/importmap отмечаются отдельно. Сохранённый пакет позволяет продолжить анализ без повторной загрузки исходников; при независимых изменениях базы, CDN или документации подготовьте новый пакет и сопоставьте хеши входов.

## 3. Подготовить и проверить кандидат

Редактируйте только нужные главы в `content/chapters/`, JSON примеров и их Markdown-копии. При изменении поведения Core обновите действующие ограничения и browser-проверки. Удалённое имя не заменяйте выдуманным классом; используйте штатную композицию и явно опишите её.

После разбора примените `candidate-manifest.json` к `content/reference/source-manifest.json` как часть рабочего кандидата. Не меняйте только хеши ради прохождения проверки. Справочники, HTML и метки версии пересобираются автоматически:

```sh
npm run build
npm test
npm run test:browser
npm run test:layout
git diff --check
```

Во время правок используйте узкие проверки затронутого поведения; полный набор выполните на окончательном кандидате. Если изменены общие темы, reset или метрики, проверьте ширины и визуальные состояния. Логи сохраняйте целиком, модели передавайте итог и подробности ошибок.

`source-manifest.json` — единый источник версии и дат. Числа в build/test не дублируются; исторические версии в описании миграций остаются историческими. Runtime продолжает использовать настоящий CDN latest, точные контракты проверяются на документированной версии. Проверка доступности latest не доказывает совпадение его поведения с описанием.

## 4. Принять и опубликовать

Проверьте diff, соответствие объяснений коду и результаты браузера. Только прошедший проверку коммит с согласованными текстами, примерами и манифестом становится новой принятой базой. Push в main запускает существующий Pages workflow; проверьте его результат и опубликованный сайт.

В Git остаются исходники документации, инструменты и компактные метаданные. Пакеты сравнения, тестовые артефакты, собранный docs и исходники CDN не коммитятся. Исходный Core и другие проекты этим процессом не меняются.
